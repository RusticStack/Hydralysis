# RusticRE on KotOR 1.0.3.0 — usage review

Status: **documentation only.** No code changes are included in this pull request. The findings
below come from using the registered RusticRE server and the CLI against a user-owned KotOR
1.0.3.0 executable while answering a module-loader question. The game-specific analysis stays in
that project; this document records only tool behavior, with no game assets or decompiled text.

## Target

| field | value |
|---|---|
| executable | `swkotor.exe`, KotOR 1.0.3.0 |
| SHA-256 | `0290889e0cea6ebc00021c1bdb945704fc4c45afaf7fcebabb0e82ba674437e6` |
| format | PE32, x86, image base `0x400000` |
| Ghidra project | previously imported and analysed, read-only, verified by the same hash |

## What was run

PE tools, without starting a JVM:

* `fingerprint` — identified the 4,042,752-byte PE32 image, version 1.0.3.0.
* `inspect` at `va:0x67bc40` — no pdata function bounds (expected for PE32), but returned a valid
  prologue, instructions and a caller candidate.
* `strings` — located `_adx`, `_s.rim`, `zzzzzzzz.zzz` and the format strings.
* `xrefs` at the string addresses — returned four absolute reference sites for `_s.rim`, three for
  `_adx`, and three for the `_a` suffix.
* `bytes` and `disasm` — decoded the string table and validated the call sites at explicit
  `rva:` addresses.

Ghidra path, with a prepared project:

* `ghidra_query --action function` resolved the containing function for an xref.
* `ghidra_query` decompiled the module-loader function and its resource helpers.
* Cold start: 7.615 s (first query), 3.77 s on later re-starts; warm queries: 0.056–0.72 s.
* The response included the analysed function range, program SHA-256 and image base.

The practical result: RusticRE found the suffix strings and their call sites with PE tools, then
gave readable decompiler text for the loader without re-importing the binary. That is the workflow
the server is meant to support.

## What worked well

* The small catalog is a real advantage over a 200-tool surface for this kind of focused work.
* `rva:`/`va:` is explicit and the ambiguity error is clear once used correctly.
* String search plus absolute xrefs was enough to go from a literal to the loader without Ghidra.
* `ghidra_query` reuses one warm worker, verifies the executable hash, and opens the saved project
  read-only. Warm answers carry the function body, not just text.
* The PE tools are useful before any Ghidra setup exists.

## What failed or was clumsy

### 1. A dot-prefixed root fails inside Ghidra with an opaque worker exit

I configured `root` as `.../rusticre-review/.cache`. The worker exited with:

```text
ERROR Abort due to Headless analyzer error: Path element starting with '.' is not permitted
```

The CLI reported only `Ghidra exited 1 before ready; inspect .../worker.log`. The cause is
Ghidra's `ProjectLocator`, which rejects project paths containing a `.cache`-style component.
A dot-free root works immediately. This is a diagnostic gap: the user has to read the worker log
to learn a rule that could be checked before copying.

### 2. The registered MCP had no `RUSTICRE_CONFIG`

`ghidra_query` through MCP returned:

```text
ValueError: set RUSTICRE_CONFIG to a json file with root and ghidra_dir
```

The same server worked from the CLI after setting the environment variable. This is a deployment
issue rather than a query bug, but it means the registered MCP cannot decompile until the client
configuration supplies a config path. A clearer MCP-side hint (for example, naming the expected
config file or the CLI equivalent) would shorten that diagnosis.

### 3. An ordinary “no analysed function” miss retires the warm worker

Two queries for addresses that Ghidra had not analysed returned:

```text
java.lang.IllegalArgumentException: no analysed function contains 040c4a0e
```

The next query cold-started (3.77 s) because every `ok: false` response retires the worker. A
missing address is a normal query answer, not evidence that the decompiler is poisoned. This cost
a cold start for each miss and interrupted a warm session that was otherwise healthy.

### 4. PE xrefs print bare RVAs while `ghidra_query` takes VAs

`xrefs` printed source and target as `0x27c0ac -> 0x352ff0` with the image base in the header.
`disasm` requires an explicit `rva:`/`va:`, and `ghidra_query` requires VAs. Using the printed
value directly as a VA produced `VA is below this image's base`. The explicit input syntax is
good; the output could label its address space so the next call is unambiguous.

### 5. PE32 `inspect` has no function bounds

For this 32-bit image, `inspect` says:

```text
no pdata function contains ...
```

That is documented in the README (PE32 function boundaries need saved analysis), and `disasm` and
`callers` still returned useful data. It is not a regression, but it is the reason `inspect` is
not a complete substitute for a saved-project function dossier on PE32.

## Proposed follow-ups

These are proposals only; none is implemented in this PR.

### A. Keep the warm worker after an ordinary miss

* Treat `java.lang.IllegalArgumentException: no analysed function contains ...` as a normal
  response: return the error and keep the worker.
* Continue to retire on decompiler refusals, timeouts, transport failures and worker death.
* Add a test that a miss leaves `stop` uncalled and the next query is warm.
* Update the README sentence that currently says every failed query retires its worker.

This is the strongest candidate: it is a behavior fix with a clear test, no API change, and it
directly removes the extra cold starts seen on KotOR.

### B. Reject a dot-prefixed Ghidra root before copying

* Add a small helper in `ghidra.py` that finds a path component beginning with `.`.
* Call it before `GhidraRunner._claim` and before `QueryRunner._start` creates a snapshot.
* Raise an actionable error such as: “Ghidra cannot open a project under a dot-prefixed path
  component '.cache'; set root to a path without dot-prefixed directories.”
* Add a unit test for the helper/claim path and a README note.

This is a guardrail, not new capability, but it turns an opaque worker exit into a one-line fix.

### C. Label PE xref address spaces (optional)

Print `rva:0x...` and `va:0x...` (or an explicit `rva`/`va` column) so the output can be passed to
the next tool without guessing. This changes output formatting and should be treated as a separate
decision.

### D. MCP configuration guidance (documentation, not code)

Document the `RUSTICRE_CONFIG` requirement at the MCP registration point, including a minimal
config with `root`, `ghidra_dir`, `java_home` and one target. The config itself is environment
specific and should not be committed.

## When I would still use REA

RusticRE intentionally does not implement p-code, basic blocks, value-flow/def-use tracing or a
full function dossier with those facets. For questions that need to know how a value moves through
a function, which basic block dominates a call, or how a decompiler expression lowers to p-code,
REA remains the better call. That is an analysis gap, not a tool-count problem: adding those
facets would grow the server beyond its current scope.

## When I would still use Ghidra

RusticRE opens a copy of an already analysed project read-only. It does not import or analyse a
fresh binary, and it does not save symbol or comment edits. For the first import and analysis, for
interactive type recovery, and for persisted renames/comments, Ghidra remains the right tool. The
KotOR project had to be prepared separately; RusticRE was fast only because that work already
existed.

## Where RusticRE fits

RusticRE is the first call for quick PE facts, string and xref hunting, hook-byte/prologue checks,
and bounded decompilation against a saved project. It keeps the context small, makes the build
hash explicit, and does not re-import on every question. REA remains the deeper analysis tool, and
Ghidra remains the authoring/initial-analysis environment.

## Evidence boundary

* The executable is user-owned and was not modified.
* No game, hook or Ghidra import was launched for this review.
* The Ghidra project was opened read-only from a snapshot; no saved symbols or comments were
  changed.
* This PR contains no game assets, saves, extracted data or decompiled program text.
* The specific loader findings remain in the KotOR project rather than this tool repository.

## Conclusion

The core RusticRE workflow is useful and should stay small. Two small changes are worth doing:
keep the warm worker after an ordinary miss (A), and reject a dot-prefixed root before copying (B).
The xref address-space label (C) and the MCP config guidance (D) are secondary. The analysis gaps
that still justify REA and Ghidra are deliberate and should not be filled by copying their tool
surfaces into RusticRE.
