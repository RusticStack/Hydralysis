# Query saved analysis

For an existing analysed project, register it in place: `prepare --adopt <.gpr, its folder or a parent> --exe <path> --target <name>` (or `--sha256` and `--program`). Nothing is copied or imported; the program's stored hash and analysed flag must match. For a new executable, explicit `prepare` owns the one-time import/analysis as a durable job, and `prepare --plan` is read-only. Do not start preparation when the user only asks for tool design or lightweight inspection. After that:

1. `ghidra-query --target <name> <VA>` for decompilation; `--action function`, `functions` or `xrefs` for analysed facts. Addresses are numeric VAs or `rva:`/`va:`. Continue incomplete enumeration with the returned `--cursor`; do not list whole tables by name.
2. Value flow: `--action pcode` gives op/varnode ids; `--action trace` with `{"seed": ..., "direction": "backward", "brief": true}` follows them through memory and into callers. A stop is not a proof of absence.
3. Virtual calls: `vtables` (which tables hold a function), `vcalls` (sites of a slot offset, receivers verified when asked). Field writes: `writes`.
4. Corrections: `type_edit` with a `source`, flat options next to `kind`. Bulk types: `import_types` with a corpus. Undo: `revert` with the overlay ids. Every client reads the corrected program; the analysed project is never written.
5. Two builds: `diff` with `against` the older target, then transfer names or a hook table.
6. A deliberate custom script: `ghidra-run --target <name> Script.java <arguments>`. It runs contained on the warm engine: its changes are rolled back and never saved, but while it runs, other clients can see them. Check its output and exit.

The engine is Hydra Engine, a Ghidra fork; no stock Ghidra is used or needed. One engine serves every client and keeps programs warm. Concurrent edits are serialized (no corruption was seen in the tests listed in the README), and `expect_revision` (the `view_revision` from `status` or the last edit) is mandatory on every edit and revert; a stale one is rebased if no later edit touched its subject, else a conflict naming the editor. `backend status` shows it; `backend stop` stops it. A timeout or a truncated page is not a result: narrow the query. Use `export` for durable bulk artifacts and `job` for progress/cancel, rather than sending an entire decompile corpus to MCP output. No project directory component may start with a period. **Agent identity.** Pass a distinct `options.as` for each editing sub-agent: without it every sub-agent of one MCP server process shares the process default view `<client name>@<boot id>` (it is not the `shared` view), sees the others' unpublished edits, and is protected from overwriting them only by `expect_revision` and the subject-aware rebase, which is conflict control and not isolation. An agent without a view reads the sealed master; `HYDRALYSIS_AGENT_ID` keeps one id across restarts, and `status show=views` lists the orphaned views a restarted server can adopt with `options.as`. A one-shot `hydralysis` command is a new agent: every invocation is a new process with a new default id `cli@<boot id>`, so an edit made by one command is not read by the next one (it reads the master and lists the earlier view as `adoptable`). Scripts and people who edit through the CLI or `hydralysis call` must set `HYDRALYSIS_AGENT_ID` or pass `options.as` on every call to keep one view across invocations.
