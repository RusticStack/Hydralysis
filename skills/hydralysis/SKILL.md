# Hydralysis

Call `hydralysis`. PE operations take `--exe`; saved-analysis operations take a configured or prepared `--target`. Quote the full build SHA-256 with every address. Use explicit `rva:0x...` or `va:0x...`; ambiguous bare PE addresses are refused and bare Ghidra addresses mean VA. For a fresh executable, `prepare --exe <path> --target <name> --plan` inspects the proposal without starting work. Explicit `prepare` starts a durable one-time setup/import/analysis job; `job <id>` reports progress/errors or requests cancellation. Only start expensive preparation when the user's task authorizes it. Never import merely to answer a query.

1. `fingerprint` and `sections` before anything else, so the build is known.
2. One function: `inspect --exe <path> <address>`. That is x64 unwind bounds, prologue, instructions and candidate callers, with no JVM. PE32 bounds and confirmed references need saved analysis.
3. A string, a caller, or a callee that `inspect` did not show: `strings`, `xrefs`, `callers`, `callees`.
4. A hook: `sigscan "48 8B ?? 24 10"`, then `prologue <address> --expect "..."`, or one `--checks-file` table. A mismatch means do not hook. Runtime probes additionally require the module hash and exact matching live bytes.
5. Decompiler text: `ghidra-query --target <name> <VA>`. It verifies the target hash and analysed flag and answers from the shared warm engine. `--action functions` and `--action xrefs` return bounded pages; continue with the returned `--cursor`. Register an analysed project with `prepare --adopt`; never re-import to answer a query.
6. A proved name: `evidence-add` with the disassembly line or the script line in `--source`.

Use query actions `dossier`, `blocks`, `pcode`, `trace`, `types`, `type`, `variables`, `data` and `scan` for deeper evidence. `type_edit` persists cited build-bound overlays in the caller's own view (a working copy of the analysed project that other agents do not read until it is published), including atomic batches and `import_types`; it never writes the analysed project. Edits are serialized (no corruption was seen in the tests listed in the README), and `expect_revision` (the `view_revision` from `ghidra_query status` or the last edit answer) is mandatory on every edit and revert, `shared` view included: a missing value is an error naming the current revision, a stale one is rebased when no later edit touched its address or type (`rebased: true`) and otherwise a conflict naming the editor and the subjects that changed. An edit refused with `stale_view` (`master_generation_changed`: another view published while yours holds records on the older generation) recorded nothing and is not retried by Hydralysis: rebase with `type_edit kind=rebase` (the call in the refusal's `next`), then send the edit again with the revision the rebase answers. Reads of a stale view keep answering from the generation it is based on plus its own records (never `stale_view`, never the head); if that generation was removed, the read is refused with `base_unavailable`, whose `next` is the rebase. Named views isolate one agent's annotations; they are not merged back. `vtables`, `vcalls`, `writes` and `diff` cover virtual calls, field writes and a second build. `export` starts a resumable file job for bulk results. Use `--options-file` and `backend help` for option details rather than inventing arguments. Use `runtime` for verified attach/spawn, typed reads, probes with captures or samples, live patch checks, cooperative breaks, continuation/unload/detach; CPU stepping/watchpoints are unavailable. Scripts use `hydralysis.client` or `hydralysis call <tool> --args <json>`. Install only engines through `backend install`, never other MCP packages. The analysis engine is Hydra Engine (a Ghidra fork); stock Ghidra is neither used nor needed, and a stock-Ghidra setting in the config or environment is ignored (`backend inspect` lists it under `ignored`). There is no GUI: Hydra Engine is headless only. Use `ghidra-run` for deliberate trusted scripts the bounded actions do not cover; a script's changes are rolled back and never saved, but while it runs, other clients can see them. A timeout, truncated output or byte-scan candidate is not a proved result. **Agent identity.** Pass a distinct `options.as` for each editing sub-agent: without it every sub-agent of one MCP server process shares the process default view `<client name>@<boot id>` (it is not the `shared` view), sees the others' unpublished edits, and is protected from overwriting them only by `expect_revision` and the subject-aware rebase, which is conflict control and not isolation. An agent without a view reads the sealed master; `HYDRALYSIS_AGENT_ID` keeps one id across restarts, and `status show=views` lists the orphaned views a restarted server can adopt with `options.as`. A one-shot `hydralysis` command is a new agent: every invocation is a new process with a new default id `cli@<boot id>`, so an edit made by one command is not read by the next one (it reads the master and lists the earlier view as `adoptable`). Scripts and people who edit through the CLI or `hydralysis call` must set `HYDRALYSIS_AGENT_ID` or pass `options.as` on every call to keep one view across invocations.
